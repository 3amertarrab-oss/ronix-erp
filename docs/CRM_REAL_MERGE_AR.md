# خطة الدمج الحقيقي لـ CRM RONIX

## الهدف

واجهة واحدة وملف مشروع واحد يربطان العميل والعرض أو العقد والتشغيل والمطالبات والقبض والتكلفة، مع بقاء كل حركة مالية ومستند معتمد قابلًا للتتبع والرجوع.

## مصادر الحقيقة

- **العرض أو العقد 1007:** المصدر الثابت للنطاق والبنود والعملة والقيمة وجدول الدفعات. بعد الاعتماد لا يُعدّل؛ التصحيح يكون بإصدار أو ملحق جديد.
- **حسابات V20:** المصدر المالي للمطالبات والقبض والتخصيصات والدفعات بعد الربط الصريح بالمشروع.
- **تشغيل R42:** المصدر للمشروعات والمهام والساعات والمراجعة والإقفال الفني.
- الربط يتم بالمعرّفات الثابتة، لا باسم العميل أو المشروع، ولا تُجمع قيمة قديمة وجديدة إذا كانتا تمثلان الحركة نفسها.

## مراحل التنفيذ

### 0. حماية البيانات

1. نسخة احتياطية كاملة قبل كل نقل، مع رقم المراجعة وSHA-256 وعدد السجلات.
2. تقرير مطابقة لكل عملة: العقود، المطالبات، المقبوض، التخصيص، دفعات الموردين والقيود.
3. تنفيذ النقل أولًا على قاعدة مرشحة مستقلة؛ قاعدة الإنتاج لا تتغير أثناء المعاينة.
4. أي سجل بلا معرّف واضح أو له أكثر من تطابق يوقف النقل ولا يُربط بالتخمين.

### 1. غلاف واجهة واحد

- شريط RONIX الرئيسي والقائمة الجانبية الخارجية هما التنقل العام الوحيد.
- محرر العقود والحسابات يعملان بوضع مضمّن يحذف الرأس والقائمة العالمية المكررة، مع إبقاء خطوات المستند وتبويبات الحسابات داخل الشاشة.
- لا يتغير في هذه المرحلة أي محرك حساب أو API أو بنية بيانات.

### 2. ملف مشروع موحد للقراءة

تظهر صفحة واحدة للمشروع تضم:

1. هوية العميل والمرجع التجاري المعتمد.
2. نطاق العقد وجدول الدفعات.
3. التشغيل والمهام والساعات والاعتمادات.
4. المطالبات والقبض والتخصيص والرصيد.
5. الموردين والتكلفة والربحية.
6. سجل زمني يوضح من نفذ كل عملية ومتى.

هذه الصفحة تجمع القراءات فقط، ولا تنسخ الأرصدة إلى مصدر جديد.

### 3. أوامر مالية وتجارية دقيقة

تستبدل الكتابة الجماعية بأوامر مستقلة ذات معرف إعادة آمن: اعتماد مستند، تسليم للحسابات، إصدار مطالبة، إثبات إرسال، تسجيل قبض، تخصيص قبض، فاتورة مورد، دفعة مورد، وإقفال. كل أمر يتحقق من المراجعة الحالية ويكتب سجل تدقيق.

### 4. نقل تدريجي إلى جداول D1

تضاف جداول جديدة دون حذف `app_state`. يجري backfill ثم مقارنة ظل بين النتائج القديمة والجديدة. تتحول القراءة ثم الكتابة وحدة بوحدة بعد نجاح المطابقة. تبقى لقطة JSON القديمة نقطة رجوع حتى مرور إصدارات مستقرة.

### 5. القطع والرجوع

قبل القطع النهائي: تجميد كتابة قصير، نسخة أخيرة، تقرير فروق صفري، تجربة كاملة من عرض سعر إلى قبض، ثم تفعيل الجداول الجديدة. أي فشل يعيد مؤشر القراءة إلى اللقطة السابقة دون إعادة تفسير التاريخ.

## قواعد لا يجوز كسرها

- لا حذف ولا تعديل رجعي لعقد معتمد أو قبض مرحّل أو قيد أو دفعة مورد.
- لا ربط بالأسماء ولا جمع مصدرين يمثلان الحركة نفسها.
- لا تغيير عملة أو سعر تحويل بعد إنشاء الحركة؛ التصحيح بحركة عكسية أو إصدار جديد.
- لا استعادة مباشرة إلى الإنتاج من ملف لم ينجح فحص سلامته ومعاينته.
- لا نشر نقل بيانات حقيقية مع دخول مالك عام دون حماية وصول.

## بوابات القبول

- تطابق إجماليات كل مشروع وكل عملة قبل النقل وبعده.
- عقد واحد معتمد ينتج تسليمًا ماليًا واحدًا، ولا يكرر المطالبات أو المقبوضات.
- تعارض التعديل يرجع 409 ولا يحفظ نصف العملية.
- الطباعة وPDF والعربية والإنجليزية والجوال تعمل من الغلاف الموحد.
- اختبار كامل: عرض → عقد → اعتماد → تشغيل → مطالبة → قبض → تخصيص → إقفال.
